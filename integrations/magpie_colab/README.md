# Magpie Colab DeepSeek integration

This integration adds a Magpie page for the on-demand `llm.py` controller. It displays the controller state and Colab CLI balance and saves settings for the next GPU session. It requires a working Colab CLI OAuth login, a separately configured Magpie OpenAI-compatible provider pointing at the controller's loopback endpoint, and a local service manager. Installation of this plugin alone does not configure those dependencies or authenticate Colab.

## Components

- `controller.py serve` wraps the project controller, reads `magpie-settings.json`, and freezes its settings in `magpie-active-settings.json` for the life of each session. It starts a GPU only for an authenticated inference request.
- While the session is idle, the controller periodically checks the model backend. Three consecutive failures stop the session so a dead model process does not leave the GPU allocated until the normal idle timeout.
- The controller estimates G4 cost using 10.05 compute units/hour, measured on the current account; Colab may change the actual rate. Check `colab usage` for the current rate and balance.
- The optional experimental 1M profile for ISTA with the AtomicChat patch, images and DSpark uses a 68,864 MiB expert cache, UBATCH=512, DYN=80 and a 128 MiB index-query chunk. Full-code generation improved about 6–8% in the tested cases, with a 2.5% longer million-input cold first-token wait. See the [latest 1M measurements](../../docs/benchmarks/colab-1m-dynamic-20261106.md) for output differences, memory and prefix-cache limitations. Other configurations retain their existing settings.
- `panel.py` listens on `127.0.0.1:18082` and serves status, settings and a bounded tail of the controller's local `llm.log`. The page can pause or resume its five-second log refresh and refresh status manually from the header. Logs are read locally, with secrets redacted; reading them does not contact or wake Colab. Run it under the same unprivileged account and `LLM_STATE` as the controller. Magpie's page service proxies access to this endpoint; do not expose this port publicly.
- `refresh.py` runs as Magpie's unprivileged user and refreshes the provider when effective capabilities change. Give its service `MAGPIE_WEB_KEY` through a protected environment file and optionally `COLAB_MAGPIE_WEB_URL` (default `http://127.0.0.1:3430`); it calls the running gateway's authenticated Fetch models API on loopback, so cached capabilities actually change. It refuses non-loopback origins. Without that key it falls back to the CLI using Magpie's `HOME` and `XDG_*`, which updates disk caches but may leave an already-running gateway stale until Fetch models is invoked there. Set `MAGPIE_BIN` and `COLAB_MAGPIE_PROVIDER` when needed. Metadata refresh never starts Colab.
- Install the plugin folder with `magpie plugin add /absolute/path/to/integrations/magpie_colab` and enable it. Its host entry is needed by Magpie's page-service proxy. Launch the controller and panel under your service manager and arrange the CLI binary and runtime state with `LLM_COLAB`, `LLM_STATE` and `HOME` as needed. Restart the panel after updating its HTML.

The single model is `deepseek-v4.1-flash-sec`, exposed as `colab-ds41/deepseek-v4.1-flash-sec` when the provider is named `colab-ds41`. Model metadata declares reasoning support and the `low`, `high`, `max` levels separately from the default `max`. Refresh each gateway's model catalog and the client's discovery cache when relaying through another Magpie. The native server alias in `vm/serve.sh` matches the controller's model ID; changing this alias does not require rebuilding the cached engine.

Select the new model ID in existing clients when upgrading. The former `ds41` and `ds41-max` model IDs are retired; disable their fully qualified IDs at the gateway as well, so stale client configurations cannot wake Colab.

For this integration, a cold inference request starts Colab once in the background and immediately returns HTTP 429 with a JSON error, including for streaming requests. It does not send a 200 SSE prelude or retain the message for later execution. Retry the request after `Retry-After: 10`. The human-readable error includes the current stage and approximate remaining time, while `server_status` provides state, phase, VM-created flag, elapsed time, estimated remaining seconds and estimate source. Only ready requests enter inference; startup, shutdown and tunnel recovery return retry responses. A failed start's cooldown returns 503. Model listing never starts Colab. The standalone `llm.py` CLI retains its original wait-and-stream behavior.

Startup estimates use up to five recent successful starts for the same model/features/context, stored privately in `state/startup-timings.json`. Without history the initial estimate is 180 seconds; this is not a guarantee. After an estimate is exceeded the remaining time becomes null and the message says it cannot reliably estimate, rather than showing a false countdown to zero. Gateways and clients may reformat errors or retry automatically; the stage is repeated in `error.message` so it remains readable when extra JSON fields are omitted.

For immediate retry responses, configure `magpie provider set colab-ds41 patience=off` on the Colab gateway and the corresponding remote provider's `patience=off` on every relay. Disable that provider's quota-rest caching (`limitRestOff=true` in its advanced settings) so repeated cold-start requests get fresh status instead of an old cached refusal. Keep the 10-second `Retry-After`: it is longer than Magpie's short same-provider retry window. Otherwise a gateway may hold a 429 internally for about a minute. These settings concern this Colab route only; client-side automatic retries are controlled separately by the client. Current Magpie versions can reformat the error and omit `server_status`, so clients must still receive a useful stage and ETA in `error.message`.

The page offers three context tiers: 262,144 tokens per request with two decoder slots, 524,288 with one, and experimental 1,048,576 with one. When ready, all accept at most four in-flight inference requests, including backend queueing; an additional request gets HTTP 429 and can retry after one completes. Four accepted requests are not four full-window decodes at once. The default tier is 524,288, with ISTA + AtomicChat, images, DSpark and maximum reasoning effort enabled.

The same patched-ISTA/image/DSpark combination at 262,144 uses two decoder slots, UBATCH=1024, a 73,000 MiB MoE cache and DYN=166. Complete short-code throughput increased from 112.29 to 121.46 tok/s in three-repeat tests; actual 229K-input prefix-cache-hit complete code improved from 104.85 to 108.70 tok/s in one sample. Cold prefill was about 7% slower, with more RAM/VRAM headroom. Other model/feature combinations retain their existing layout. See the [256K measurements](../../docs/benchmarks/colab-256k-20261106.md) for sampling settings, output differences and concurrency limits.

The patched ISTA image-and-DSpark configuration at 524,288 uses one decoder slot, UBATCH=512, a 73,000 MiB MoE cache and DYN=166. Final complete-code rates were 104.54 tok/s for short input, 89.79 for cold 480K input and 91.23 after a prefix hit. See the [512K measurements](../../docs/benchmarks/colab-512k-dynamic-20261106.md) for sampling, output-length and latency tradeoffs. Other model variants and feature combinations retain their prior profiles. These checks do not establish long-document reasoning accuracy or sustained reliability.

The controller separates configured defaults from the public rollout ceiling. The 256K context defaults to 65,536 output tokens; 512K defaults to 131,072. The configured 1M default is 262,144, **pending validation and later explicit release approval**: its current effective default is 131,072. The controller rejects requests above 131,072, including 256K output on 1M context, with HTTP 400 before acquiring a GPU; both relay catalogs advertise the 131,072 ceiling. There is no public opt-in flag. `max_output_tokens` metadata always advertises the effective ceiling, while the controller and page also expose the configured default and pending flag. Smaller explicit budgets remain valid. All three generation routes validate `max_tokens`, `max_completion_tokens`, `max_output_tokens` and `n_predict`, reject multiple simultaneous limits, and normalize the single limit to the route canonical field (`max_output_tokens` for Responses, `max_tokens` otherwise). This also blocks a native `n_predict` extension from overriding a Responses cap after conversion. The budget includes thinking, visible text and tool-call output, and a larger cap does not force longer thinking. Configure both gateways and the client for the actual public budget: `magpie model output 'colab-ds41/*' 131072`, refresh the running catalogs, and update a client's old explicit 32K limit. Native long-output validation is restricted to the isolated benchmark and does not change this public policy.

Input and output share the context window. With current effective defaults the maximum input budgets, including templates/history/tools, are 196,608 / 393,216 / 917,504 at 256K / 512K / 1M. The page suggests earlier client compaction at 180,000 / 360,000 / 840,000. Configure the client that compacts history; these hints are not automatic server-side history truncation. For OMP's current 512K model, use a scoped `maxTokens: 131072` override and `compaction.modelThresholds` entry `"f360000"` for that exact provider/model, preserving other models' settings. Recompute client reservations when changing context or output tiers. The controller's upstream socket wait is two hours; generated OpenCode settings use a two-hour header wait and 30-minute chunk wait. Long requests should stream: Magpie's own vendor response-header timeout is ten minutes for non-streaming responses. These are wait limits, not a promise that all four worst-case long requests finish within a bound.

Earlier saved contexts are retained for an already-running session. For the next session, legacy 32K/64K/128K settings map to the 262,144 tier; saved 256K, 512K and 1M choices are preserved. Saved changes apply to the next session; an active session keeps its original snapshot. The idle timer starts after the last request completes; the maximum runtime is a local forced-stop threshold and can interrupt active requests. Google may end a session earlier. A 24-hour selection does not guarantee eligibility or duration. The minimum balance is checked at startup and is not a spending cap.

For the page-service design, see [Magpie's plugin documentation](https://usemagpie.ai/docs/plugins) and the [community chat page](https://github.com/Magiczerowxy/magpie-chat). Treat the Colab OAuth token and all gateway keys as secrets; do not include them in plugin configuration or repository files.
