# G4 256K tuning, 2026-11-06

The selected profile passed the checks below and is applied only to the patched-ISTA/image/DSpark 256K configuration. The default context remains 512K; the optional 1M profile is unchanged.

## Fixed conditions

ISTA IQ2_XXS + AtomicChat, image input and DSpark enabled, draft depth 2, cached b11963 build. Each decoder slot has 262,144 total input-plus-generated tokens; two slots share a 524,288-token allocation. Four accepted clients may queue. No model, quantization, routed-expert-count or C++/CUDA changes were made. DMA remains disabled as required by the image path in `vm/serve.sh`.

Short screens use max reasoning effort, 512 output tokens, temperature 0, top_p 1, seed 42, alternating the same code and prose prompts three times each. See [the prompt texts](colab-1m-20261106.md#prompts). All short outputs end by length in reasoning, so these are generation measurements, not completed tasks. Each screen also runs the complete LRU code task at max effort, temperature 0.6 and a 32,768-token output budget. Temperature 0 had previously exhausted the baseline budget without an answer; production sampling defaults are unchanged.

Cold first-token timings start with the model already loaded. Downloads and GPU/model startup are additional. Long-input fixtures use repeated filler and do not establish real-world long-document quality. Profiles use separate fresh G4 sessions; hardware/session variation remains a limitation.

All six complete code examples stopped normally and passed basic capacity, update, recency and eviction checks. This is a toy code check, not a broad coding benchmark.

Reducing UBATCH alone did not improve short decode and increased 128K first-token time by about 30%. At cache 73,000 and UBATCH 1024, increasing DYN from 110 to 166 coincided with about 8–9% higher short decode. Baseline/DYN-110 short output hashes match each other; all DYN-166 short hashes also match each other but differ from the DYN-110 family. Thus the cross-family speed difference is observed workload throughput, not a strict identical-token causal measurement.

The 73,000/1024/166 candidate generates the same complete 4,427-token code output as 74,231/1024/166, with 1,228 MiB more minimum free VRAM and about 1% lower decode throughput in these screens. This candidate was selected for further qualification. Its main GPU compute buffer is smaller than the original UBATCH-2048 allocation; more room can go to adaptive expert cache while retaining two decoder slots.

## Buffer allocation and expert residency

Lowering UBATCH from 2048 to 1024 reduced main GPU compute buffers from 7,459.52 to 4,420.76 MiB and host compute buffers from 1,977.46 to 986.73 MiB. At cache 73,000 / DYN 110, 8,120 experts (64.77 GiB) were pinned, but short decode barely changed. Increasing DYN to 166 at the same cache and batch pins 7,839 experts (62.44 GiB), close to the baseline's 7,814 (62.32 GiB), while leaving more space for adaptive misses. Actual dynamic slots per group are `166 111 166 166 166 166 55 55`, with per-group caps; not every group gets 166.

This profile uses the reclaimed buffers to grow adaptive cache while retaining nearly the original pinned hot-expert set. The observed speed difference still has the token-trajectory and separate-runtime limitations described above.

## Full qualification

Fresh baseline and selected-candidate sessions used the same validation order. Speeds below are server timings including reasoning; full-code checks use temperature 0.6, top_p 1, seed 42, max effort and a 32,768-token budget. Input sizes are reported by the engine, not inferred from the configured window.

| Measurement | Original 70,430 / 2048 / 110 | Selected 73,000 / 1024 / 166 | Observed change |
|---|---:|---:|---:|
| Complete short code, mean of 3 | 112.29 tok/s | 121.46 tok/s | +8.17% |
| Complete code after 229,093 input tokens, once | 104.85 tok/s | 108.70 tok/s | +3.67% |
| Four short queued clients, code, combined 2 waves | 147.77 tok/s | 150.98 tok/s | +2.17%, small relative to wave variation |
| Four short queued clients, prose, combined 2 waves | 125.42 tok/s | 139.47 tok/s | +11.20% |
| 131,137-input cold first token | 44.11 s | 47.32 s | 7.27% slower |
| 229,093-input cold first token | 79.80 s | 85.62 s | 7.30% slower |
| Minimum free VRAM | 1,428 MiB | 2,172 MiB | more headroom |
| Minimum available host RAM | 2.306 GiB | 3.720 GiB | more headroom |

The three baseline short-code answers each generated 5,056 tokens with one matching hash; the selected profile generated 4,427 each with a different matching hash. The filled-context code outputs used 3,981 versus 2,785 tokens. All completed-code examples passed basic LRU checks, including both filled-context examples. Different output lengths and trajectories mean total task-time changes must not all be attributed to engine speed. Filled-context complete code is a single sample per profile, not a universal near-full-window rate.

A separate max-effort, temperature-0 short-code diagnostic exhausted 32,768 tokens without a visible answer on the baseline. The selected profile stopped normally after 6,106 tokens at 125.63 tok/s, with working visible code. This is an observation for this fixed case, not a general fix for long reasoning. Both temperature-0 appended prose turns still exhausted their budgets with no visible answer (28,558 / 29,754 tokens; budgets conservatively reserved remaining context). Those are unfinished tasks, not completed-prose speed measurements. Earlier messages and generated code differ between the appended turns, so they are not identical histories.

The four-client probes each request 1,024 output tokens and use short inputs. All finish by length in reasoning, with no visible answer. Aggregate throughput is total generated tokens divided by total wave time; it is not per-request speed or four full-window simultaneous decodes. Baseline code waves were 142.84/153.06 tok/s and selected waves 149.25/152.75, so a robust code-concurrency gain is not established by this small difference.

### Near-full requests and image checks

Two requests were submitted together, each with 261,703 input tokens, distinct three-record fixtures at approximately 10%, 50% and 90% of the filler, and an arithmetic answer. Both profiles returned all records and arithmetic correctly. These overlapping requests exercise the two slots and their stored contexts; they do not establish continuous joint decoding of two full windows.

The first-starting response pauses while the other prompt is being processed. Its server generation rate includes that interruption (2.92 / 5.18 tok/s); these values are not standalone decode rates. Scheduling and prefill contention remain relevant to long-input concurrency. This synthetic test is not a realistic multi-document reasoning evaluation.

Both 1024×1024 and 4096×4096 red-image probes passed, and the post-long-input image probe also passed. These separate image requests do not cover simultaneous multi-image or image-plus-full-text workloads. Resource sampling found no OOM: full-memory PSI avg60 peaked at 0.01 / 0.03, with 250 / 193 samples. This is limited-duration qualification, not a long-term reliability guarantee.

## Applied scope and evidence

Only 262,144 + ISTA + AtomicChat + images + DSpark receives the selected override. It retains two decoder slots and the four-in-flight admission limit. Unpatched ISTA, Abiray, disabled-image/draft combinations and other contexts keep their existing profiles. The default is still 524,288; its 70,430/512/110 profile and the optional 1M 66,000/512/50 profile are unchanged. No new compiled cache is required.

The source has 61 passing offline regression tests, including scope/fallback and two-slot checks. See [sanitized machine-readable results](colab-256k-20261106.json) for all six screens and both full validations. Private infrastructure and credentials are excluded. Output-hash differences across parameter families and between some cold/cache-hit runs were observed; their numerical source was not localized, so bit-identical generation or broad quality equivalence is not established. Separate G4 sessions and the small workload set limit attribution and generalization.
