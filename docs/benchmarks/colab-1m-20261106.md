# G4: 1M context tuning, 2026-11-06

After these measurements, the user selected 512K as the default and retained 1M as an optional experimental tier. The observations and original tuning decision below describe that historical benchmark run.

The default 512K profile was subsequently tuned to 73,000 MiB cache / UBATCH 512 / DYN 166. See [the later 512K experiment](colab-512k-dynamic-20261106.md); the measurements below retain their original configuration and are historical.

The optional 1M profile was later tuned separately to 68,864 MiB cache / UBATCH 512 / DYN 80 with a 128 MiB index-query chunk. See [the later 1M experiment](colab-1m-dynamic-20261106.md); statements below about keeping the 66,000/512/50 profile describe the earlier decision.

This is an exploratory result for the patched ISTA configuration. At the time of this benchmark, the Magpie page exposed only 262,144 and 524,288 tokens. The 512K cache improvement is already in `49ae6f5`; these 1M experiments do not justify copying that configuration blindly into 1M.

## Applied 512K change

For patched ISTA with images and DSpark at 524,288 tokens, commit [`49ae6f5`](https://github.com/imDaniel/deepseek-colab/commit/49ae6f537bd598fb3850359462afd44445ab67a0) increases MoE cache from 64,000 to 70,430 MiB and DYN from 50 to 110, retaining UBATCH 512 and a single decoder slot. No kernel, weight, precision or routed-expert-count change was made. The larger cache can keep more experts on the GPU; DYN tunes the cache's dynamic reservation. These two settings were validated together, so their individual contributions were not isolated.

Matched-output high/256 short tests (three repeats per task) improved code from 93.57 to 103.02 tok/s and prose from 69.39 to 82.92 tok/s. A complete max-effort code sample improved from the previous three-run mean of 89.09 to 101.40 tok/s with the same 4,224-token output. Four short queued clients and a synthetic 524,062-token input passed; these do not establish broad long-document reasoning quality. Baseline and candidate used separate G4 sessions, so hardware/session variation remains a limitation.

- Cached llama.cpp b11963 source `39febd2adb947b70da35e95f9351b3bf58ad170a`, build archive SHA-256 `fe01a69712365f81331b71e9e1409f27182a92b808fcbe123df5f1c48de10aa8`. No C++/CUDA rebuilds for these parameter tests.
- 1,048,576 total input-plus-generated tokens per slot, one decoder slot. A full 1,048,576-token input cannot also reserve 32K output. Four clients can queue; this does not mean four full-window decodes at once.
- Same-runtime loopback HTTP; server generation timings include reasoning. These are not public Magpie end-to-end measurements.

Short screens use the fixed code/prose prompts below, temperature 0, top_p 1, seed 42, `reasoning_effort=high`, budget 256, three repeats per task. A separate complete-code check uses max effort and a 32,768-token budget. These explicit deterministic sampling settings differ from the measured server defaults (temperature about 0.8 and top_p about 0.95); no production sampling default was changed. `finish=length` with no visible answer is an unfinished task, even when HTTP/SSE completed normally.

Cold first-token timings below start with the model already loaded and ready; GPU allocation, download and model loading are additional startup costs.

The filled-context prompt is identical across fresh runtimes: `Benchmark fixed-million. Read the repeated filler: ` + `" a" * 1000000` + `\nEnd of filler. ` + the code prompt. The server reports 1,000,091 input tokens. It is run once cold, then twice identically for cached decode. This is synthetic capacity/performance testing, not realistic long-document quality evaluation.

Reducing UBATCH from 512 to 256 reduced main GPU compute buffers from 9,226.26 to 4,573.25 MiB and host compute buffers from 1,836.86 to 918.31 MiB. It made room for more expert cache but slowed prefill. The existing compiled `LLAMA_DSV41_IDX_CHUNK_MIB=128` reduced GPU compute to 7,178.26 MiB without reducing host compute; its standalone decode improvement was below the 5% screen threshold.

The 72,000/256/110 short outputs match the baseline hashes. Its complete-code output matches the UBATCH-256 control (4,592 tokens), improving from 92.78 to 105.79 tok/s. The 74,231/128/166 output trajectory differs; its complete short code ends normally after 4,180 tokens at 111.43 tok/s. **That 111.43 value has a short input and must not be described as decode after filling a million-token context.**

## Actual decode after one million input tokens

All rows below retain draft depth 2, high effort, 256 output tokens. All 256 tokens are reasoning; this table measures generation, not completed code tasks.

| Cache / UBATCH / DYN | Cold first token | Cold decode | Cached decode, mean of two | Cached first token |
|---|---:|---:|---:|---:|
| 66,000 / 512 / 50 | 671.59 s (11.2 min) | 74.92 | 73.61 | 0.60 s |
| 72,000 / 256 / 110 | 876.03 s (14.6 min) | 79.39 | 74.39 | 0.60 s |
| 74,231 / 128 / 166 | 1,231.07 s (20.5 min) | 78.30 | 80.01 | 0.59 s |

The 74,231 row increases cached decode from 73.61 to 80.01 tok/s (about 8.7%) while increasing cold first-token latency by about 83%.

The larger-cache rows have substantially more host RAM headroom, but short-prompt gains do not carry over proportionally to a filled context. The 72,000 row's geometric decode improvement is about 3.5%; the 74,231 row's is about 6.6%, with an 83% cold-prefill increase. These are not compelling speed-default replacements for the existing 66,000 layout.

Output hashes differ across some configurations and between cold and cached runs; the source of those differences was not localized. Thus the table is observed workload throughput, not a proof that each parameter change alone caused the entire difference or that cache restore is bit-identical. Identical-request cache hits do not establish reuse after editing a question inside an earlier message.

## Functional qualification

Qualification uses the existing 66,000/512/50/depth-2 layout. All rows below use max reasoning effort and at most 32,768 output tokens, except image probes. The first two rows have the same million-token user prompt; the prose row appends the visible code answer and a second user question as ordinary Chat history, without returning prior reasoning.

| Request | Input / cached tokens | Temperature | Output / ending | Decode | First token / first visible answer |
|---|---|---:|---|---:|---|
| Million-input code, cold | 1,000,092 / 0 | 0 | 32,768, length, no visible answer | 69.55 tok/s | 679.88 s / none |
| Same code, cache hit | 1,000,092 / 1,000,088 | 0.6 | 4,752, stop, visible code | 71.33 tok/s | 0.632 s / 58.40 s |
| Appended prose question | 1,000,741 / 1,000,088 | 0 | 12,328, stop, visible prose | 62.77 tok/s | 5.259 s / 189.47 s |

The completed code passed basic capacity validation, update, recency and eviction checks after a restrictive AST review; this is not a broad code-quality evaluation. Three repeated complete short-code requests also stopped normally at 4,224 tokens, with the same output hash and 89.22/91.03/91.24 tok/s.

Both 32K append-chat probes (with and without prior `reasoning_content`) reused over 32K tokens and answered correctly. The actual million-token appended turn above demonstrates useful prefix reuse for this ordinary Chat history, rather than only an identical-request hit. Changes to earlier messages, client compaction, or cache replacement may invalidate that reuse; public Magpie client behavior was not measured here.

A 4096×4096 red image before the long tests and a 1024×1024 image after the million-token conversation were correctly identified. These are separate short image requests, not combined million-text-plus-multiple-image workloads.

Four short queued clients (75-token code / 68-token prose inputs, max effort, 1,024 output tokens each) all completed their HTTP/SSE streams. Aggregate throughput was 90.18 / 76.94 tok/s, with up to 34.27 / 40.11 seconds before the last queued request started generating. All ended by length with no visible answer; these are short generation/queue probes, not completed tasks or four simultaneous million-token decodes.

Near-window retrieval passed: 1,048,101 input tokens, with records inserted at about 10%, 50% and 90% of the filler. At low effort and temperature 0, all three record codes and the arithmetic answer were returned correctly in JSON (84 output tokens, stop). Cold first token was 739.27 seconds (12.32 minutes); total response time was 740.61 seconds. This is synthetic retrieval, not realistic long-document reasoning validation.

Final qualification sampled resources 487 times: minimum available host RAM 1.679 GiB, minimum free VRAM 2,916 MiB, full-memory PSI avg60 maximum 0, no observed OOM. Host headroom remains small; these tests do not establish long-term reliability.

## Adoption decision

The applied 512K profile remains 70,430/512/110 for the scoped patched-ISTA/image/DSpark configuration. The existing experimental CLI 1M profile remains 66,000/512/50 with draft depth 2. None of the tested replacements delivered a compelling combined decode, cold-prefill and complete-answer result, so no new 1M default or UI option was enabled. Prefix reuse helps a continuing long conversation, but a different document or another request replacing the single slot may lose that benefit.

No C++/CUDA, quantization or routed-expert-count changes were made. The existing compiled cache is sufficient. Measurements used separate G4 sessions and synthetic long inputs; the observed best throughput is not a theoretical ceiling or a universal quality/speed guarantee.
